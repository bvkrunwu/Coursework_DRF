# Habit Tracker — трекер полезных привычек

## Описание

Это учебный проект по созданию бэкенд-части SPA веб-приложения для трекинга привычек. Проект основан на принципах,
изложенных в книге Джеймса Клира «Атомные привычки», и реализует систему для формирования полезных привычек и избавления
от плохих.

## Цели проекта

- Освоить разработку REST API на Django и Django REST Framework (DRF).
- Отработать практику работы с моделями, сериализаторами и вьюсетами.
- Научиться структурировать проект по приложениям.
- Реализовать полноценную CRUD-логику для основных сущностей.
- Получить опыт интеграции с внешними сервисами (Telegram).
- Изучить работу с фоновыми задачами (Celery) и их планировщиком (Celery Beat).
- Настроить современную инфраструктуру: контейнеризацию с помощью Docker и Docker Compose.
- Внедрить CI/CD пайплайн с использованием GitHub Actions для автоматизации тестирования и деплоя.

## Текущий статус

**Этап разработки:** реализованы основные модели, эндпоинты, сериализация,
пагинация, система прав доступа, валидация,
интеграция с Telegram и Celery для рассылки напоминаний.
Проект полностью **контейнеризирован с помощью Docker и готов к
автоматическому развёртыванию через CI/CD (GitHub Actions)**.

## Этап 1: Базовая настройка и реализация моделей

### Реализовано

- Создан новый Django-проект, подключен Django REST Framework (DRF).
- Реализована модель **Привычка** (*Habit*) со следующими полями:
    - Пользователь (создатель привычки).
    - Действие (текстовое описание).
    - Место и время выполнения.
    - Периодичность (по умолчанию — ежедневно).
    - Время на выполнение (не более 120 секунд).
    - Признак публичности (для общего доступа).
    - Вознаграждение (текстовое поле).
    - Связанная привычка (*FK* на другую привычку).
    - Признак приятной привычки (булево поле).
- Реализована сложная бизнес-логика связей между привычками:
    - Полезная привычка может иметь вознаграждение ИЛИ связанную приятную привычку.
    - Приятная привычка не может иметь вознаграждения или связанных привычек.

> ⚙️ На этом этапе заложен фундамент проекта: реализована основная модель данных с учетом всех требований к валидации и
> связям.

## Этап 2: Реализация API и пагинации

### Реализовано

- Описаны эндпоинты для работы с привычками:
    - Регистрация пользователя.
    - Авторизация пользователя.
    - Создание, чтение, обновление и удаление (CRUD) привычек текущего пользователя.
    - Просмотр списка публичных привычек.
- Реализована пагинация для вывода списков привычек (по 5 элементов на страницу).

> ⚙️ На этом этапе реализована базовая логика взаимодействия с данными через API, включая навигацию по спискам.

## Этап 3: Управление доступом и безопасность

### Реализовано

- **Реализована CRUD-логика для пользователей.**
- **Настроена система прав доступа:**
    - Каждый пользователь имеет доступ только к своим привычкам (механизм *IsOwner*).
    - Пользователи могут просматривать список публичных привычек без возможности редактирования или удаления.
    - Для защиты фронтенда настроен *CORS*.

> ⚙️ На этом этапе обеспечена безопасность данных и разграничение прав доступа между пользователями.

## Этап 4: Валидация и бизнес-правила

### Реализовано

- Реализованы валидаторы для модели «Привычка»:
    - Исключение одновременного выбора связанной привычки и указания вознаграждения.
    - Проверка, что время выполнения не превышает 120 секунд.
    - Проверка, что в связанные привычки попадают только привычки с признаком «приятная».
    - Ограничение периодичности: нельзя выполнять привычку реже, чем раз в 7 дней.

> ⚙️ На этом этапе проект получил надежную защиту от некорректных данных и соблюдение логики приложения на уровне базы
> данных и сериализаторов.

## Этап 6: Контейнеризация и CI/CD (GitHub Actions)

### Реализовано

Проект полностью переведен на контейнеризацию с помощью **Docker** и **Docker Compose** для упрощения локальной
разработки и развертывания. Также настроен конвейер непрерывной интеграции и доставки (**CI/CD**) с использованием *
*GitHub Actions**.

* **Локальный запуск:** Проект запускается одной командой `docker-compose up --build`, которая поднимает все необходимые
  сервисы (Django, PostgreSQL, Redis, Celery, Nginx).
* **Автоматизация:** В репозиторий добавлен рабочий пайплайн (`ci.yml`), который при каждом пуше или пулл-реквесте:
    1. Запускает линтинг кода (Flake8) и тесты.
    2. При успешном прохождении тестов собирает Docker-образ приложения.
    3. Автоматически деплоит собранный образ на удаленный сервер по SSH.

> ⚙️ На этом этапе проект получил современную инфраструктуру для разработки, тестирования и развертывания, что
> обеспечивает надежность и удобство работы.

## Запуск проекта локально

Для запуска проекта на вашей машине необходимо выполнить следующие шаги:

1. Установите Docker Engine и Docker Compose на вашу систему.
2. Клонируйте репозиторий проекта на ваш компьютер.
3. Перейдите в корневую директорию проекта в терминале.
4. Запустите все сервисы одной командой:
   ```bash
   docker-compose up --build
   ```
5. После сборки образов приложение будет доступно по адресу `http://localhost`.

*Примечание:* Для работы некоторых задач Celery может потребоваться несколько минут на запуск после старта контейнеров.

## Настройка CI/CD и деплоя

Проект использует GitHub Actions для автоматизации процессов. Пайплайн настроен следующим образом:

1. **Линтинг и тестирование:** При каждом коммите или пулл-реквесте запускаются проверки качества кода и тесты. Пайплайн
   остановится при ошибках.
2. **Сборка образа:** Если тесты пройдены успешно, GitHub Actions автоматически собирает Docker-образ вашего приложения.
3. **Деплой:** Собранный образ автоматически отправляется на ваш удаленный сервер. Для этого в настройках репозитория
   должны быть добавлены секреты:
    * `SSH_KEY`: Приватный SSH-ключ для доступа к серверу.
    * `SSH_USER`: Имя пользователя на сервере.
    * `SERVER_IP`: IP-адрес вашего сервера.

Таким образом, после успешного прохождения тестов (`push` в ветку `main`), ваш сервер автоматически обновится до
последней версии кода без ручного вмешательства.
